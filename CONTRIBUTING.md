# 🤝 Contributing to Cs-Brazil

First of all, thank you for your interest in contributing!

Whether you're explaining a chapter from a classic Computer Science book, building a learning path, documenting a real project, or reviewing someone else's work — your contribution helps make high-quality Computer Science education more accessible to the Brazilian community.

---

## 🇧🇷 Antes de começar

A Cs-Brazil é uma comunidade colaborativa. A ideia aqui não é só armazenar conteúdo — é construir, aos poucos, uma biblioteca aberta de material didático original sobre Ciência da Computação.

Antes de começar sua contribuição, vale a pena dar uma olhada em:

- `README.md`
- `COPYRIGHT.md`
- `CODE_OF_CONDUCT.md`

---

## 🚀 Como contribuir

Toda contribuição acaba se encaixando em pelo menos um dos três pilares da comunidade.

### 📚 Pilar 1 – Livros

Explique capítulos de livros clássicos com suas próprias palavras. O foco aqui é ensinar os conceitos, não reproduzir o texto original.

Cada capítulo normalmente tem:

- README.md
- Diario-de-Estudo.md
- exercícios
- diagramas próprios

### 🛤️ Pilar 2 – Trilhas de Aprendizado

Monte um caminho organizado para aprender uma tecnologia ou área específica. Uma trilha pode combinar diversas referências diferentes.

**Alguns exemplos:**

- Linux para DevOps
- Docker para Iniciantes
- Fundamentos de Redes
- Introdução ao Rust

### 🛠️ Pilar 3 – Projetos

Explique projetos reais — pode ser:

- um projeto seu; ou
- um projeto open source de terceiros (desde que a licença permita).

Aborde:

- arquitetura
- organização
- decisões técnicas
- padrões utilizados
- dificuldades encontradas pelo caminho

E sempre indique o repositório original quando usar projetos de terceiros.

---

## 💡 Antes de começar um projeto

Pra evitar que o mesmo trabalho seja feito duas vezes:

1. Veja se já existe uma Issue parecida com a sua ideia.
2. Se não existir, abra uma nova Issue descrevendo o que você quer fazer.
3. Espere o feedback da comunidade, se for o caso.
4. Só então comece a implementação.

Simples assim — evita que duas pessoas trabalhem no mesmo conteúdo ao mesmo tempo sem saber.

---

## 🌿 Fluxo de contribuição

1. Faça um fork da organização (ou peça um novo repositório).
2. Crie uma branch:

```bash
git checkout -b minha-contribuicao
```

3. Faça suas alterações.
4. Commit:

```bash
git commit -m "Adiciona capítulo sobre Memória Virtual"
```

5. Envie sua branch:

```bash
git push origin minha-contribuicao
```

6. Abra um Pull Request.

---

## 📋 Checklist antes do Pull Request

Antes de enviar seu PR, confira se:

- [ ] o conteúdo foi escrito com suas próprias palavras
- [ ] você revisou ortografia e gramática
- [ ] os exemplos de código foram testados
- [ ] você não incluiu PDFs, EPUBs ou livros
- [ ] a licença do projeto foi respeitada (quando aplicável)
- [ ] nenhuma chave, token ou dado sensível foi publicado
- [ ] o README do repositório está atualizado
- [ ] seu conteúdo tem referências quando necessário

---

## 📁 Estrutura dos Repositórios

Cada tipo de repositório segue uma organização padrão. Dá uma olhada em `docs/repository-layout.md` e siga essa estrutura — isso mantém tudo consistente entre os projetos da organização.

---

## 📓 Diário de Estudo

Sempre que possível, registre seu processo de aprendizado. Alguns tópicos que ajudam bastante:

- onde você travou
- o que você pesquisou
- o que você aprendeu
- o que faria diferente
- quais analogias te ajudaram a entender

O objetivo aqui não é parecer perfeito — é compartilhar o caminho que você percorreu, erros e tudo.

---

## 📝 Exercícios

Quando um capítulo tiver exercícios:

- explique seu raciocínio
- descreva os erros que cometeu no caminho
- registre alternativas que você descartou
- mostre como chegou até a solução

E se a referência original não tiver exercícios, sinta-se à vontade pra criar novos desafios relacionados ao que foi estudado.

---

## 👀 Processo de Revisão

Todo Pull Request passa por revisão humana. Os revisores olham para:

- correção técnica
- clareza da explicação
- qualidade dos exemplos
- organização do conteúdo
- aderência às diretrizes da comunidade

É normal um PR receber sugestões de melhoria antes de ser aprovado — isso faz parte do processo, não é sinal de que algo deu errado.

---

## ⭐ Como se tornar Revisor

A gente precisa de pessoas com experiência em diferentes áreas da computação, como:

- Sistemas Operacionais
- Redes
- Compiladores
- Rust
- Go
- C++
- Linux
- Kubernetes
- Banco de Dados
- Arquitetura de Software

Quer ajudar revisando contribuições da comunidade? É simples:

1. Abra uma Issue.
2. Use o título no formato:

```text
[REVISOR] Nome - Especialidade
```

Por exemplo:

```text
[REVISOR] Ana - Rust / Sistemas Distribuídos
```

Conte um pouco da sua experiência e em quais assuntos você gostaria de ajudar.

---

## 💬 Discussões

Discordâncias técnicas são naturais e fazem parte do processo. Se você acha que uma explicação pode melhorar:

- abra uma Issue
- traga argumentos técnicos
- proponha uma melhoria concreta

O objetivo não é vencer uma discussão — é chegar ao melhor material possível, juntos.
